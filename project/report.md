Проект посвящён построению сервиса детекции транспортных объектов на изображениях дорожной сцены. В рамках проекта реализован полный ML-пайплайн: загрузка и подготовка данных, EDA, baseline, обучение detection-моделей, сохранение артефактов, инференс и REST API сервис. ## 2. Постановка задачи и контекст

### Предметная область и задача

Предметная область проекта - CV для анализа дорожной сцены. Основная задача это автоматическое обнаружение транспортных объектов на изображении.

Потенциальные сценарии применения:
- мониторинг дорожного трафика;
- системы умного города;
- анализ загруженности дорог;
- вспомогательные модули для задач автоматического вождения;
- первичная обработка кадров с дорожных камер.

Пользователь сервиса загружает изображение (кадр видео) дорожной сцены, а сервис возвращает список найденных объектов с координатами bounding boxes и уверенностью предсказаний.

### Формулировка задачи в терминах ML

Задача относится к классу **детекции объектов**.

**Входные данные:**
RGB-изображение дорожной сцены.

**Выходы модели:**
Список объектов, где для каждого предсказанного объекта возвращаются:
- класс объекта;
- confidence score;
- координаты bounding box в формате `xmin, ymin, xmax, ymax`.

**Классы проекта:**
- `biker`;
- `car`;
- `pedestrian`;
- `trafficLight`;
- `trafficLight-Green`;
- `trafficLight-GreenLeft`;
- `trafficLight-Red`;
- `trafficLight-RedLeft`;
- `trafficLight-Yellow`;
- `trafficLight-YellowLeft`;
- `truck`.

### Целевые метрики качества

Для оценки detection-моделей использовались метрики:
- `precision@0.5`;
- `recall@0.5`;
- `f1@0.5`;
- `mAP`;
- `mAP@0.5`;
- `mAP@0.75`;
- `mAR`.

Ключевая метрика выбора финальной модели - **`mAP@0.5`**. 
Она выбрана потому, что в задаче детекции объектов важно оценивать не только правильность класса, но и качество локализации объекта через IoU между предсказанным и истинным bounding box.

## 3. Данные

### Источник данных

В проекте используется открытый датасет:

> **Udacity Self Driving Car Dataset**

Датасет содержит изображения дорожной сцены и аннотации объектов в формате bounding boxes.

Полные raw/organized/processed данные не хранятся в репозитории из-за большого размера. Данные загружаются автоматически через pipeline проекта при наличии Kaggle API token.

### Структура данных

После подготовки данных используется структура:

```text
data/
├── raw/
├── organized/
└── processed/
    └── detection/
        ├── images/
        └── annotations.csv
```

Основной файл аннотаций:

```text
data/processed/detection/annotations.csv
```

Ожидаемые колонки:

```text
image, label, xmin, ymin, xmax, ymax, image_width, image_height
```

Где:
- `image` - имя файла изображения;
- `label` - класс объекта;
- `xmin, ymin, xmax, ymax` - координаты bounding box;
- `image_width, image_height` - размеры исходного изображения.

### Предобработка и EDA

Pipeline подготовки данных состоит из трёх этапов:

1. `download`
   Загружает исходный датасет через Kaggle API в `data/raw/`.

2. `organize`
   Организует структуру raw-данных в ожидаемый проектом формат.

3. `prepare`
   Формирует processed-слой:
   - копирует изображения в `data/processed/detection/images`;
   - создаёт единый файл `annotations.csv`;
   - нормализует названия колонок;
   - сохраняет аннотации в формате, удобном для `DetectionDataset`.

EDA выполнялся в ноутбуке:

```text
notebooks/01_eda.ipynb
```

В ходе EDA были проверены:
- структура организованных данных;
- количество изображений и аннотаций;
- распределение классов;
- размеры изображений;
- размеры и положение bounding boxes;
- соответствие изображений и аннотаций;
- визуализация bounding boxes на примерах изображений.

Основной вывод EDA: данные пригодны для обучения моделей обнаружения объектов, однако классы распределены неравномерно, поэтому для выбора модели важно учитывать не только accuracy-подобные показатели, а detection-метрики: `precision`, `recall`, `F1` и `mAP`.

## 4. Модели и подходы

### Baseline модель

В качестве baseline использовалась:

```text
Faster R-CNN ResNET50 FPN
```

с предобученными COCO-весами, без дообучения на представленных данных.

Baseline нужен для оценки качества универсальной pretrained detection-модели до fine-tuning на целевых данных. Так как модель обучалась на COCO, а классы проекта отличаются от COCO-классов, в baseline-ноутбуке выполнялся mapping COCO-классов в классы проекта.

Baseline оценивался по тем же detection-метрикам, что и основные модели:
- `precision@0.5`;
- `recall@0.5`;
- `f1@0.5`;
- `mAP`;
- `mAP@0.5`;
- `mAP@0.75`.

Baseline оценивался на validation-подвыборке из 300 изображений. Для сопоставления классов был выполнен mapping COCO-классов в классы проекта.

>Baseline оценивался на ограниченной validation-подвыборке для ускорения эксперимента, поэтому его значения используются как ориентировочная стартовая точка, а не как абсолютно равный по вычислительному протоколу full validation benchmark.

| Метрика | Значение |
|---|---:|
| precision@0.5 | 0.3562 |
| recall@0.5 | 0.5310 |
| f1@0.5 | 0.4264 |
| mAP | 0.0646 |
| mAP@0.5 | 0.1363 |
| mAP@0.75 | 0.0533 |
| mAR@1 | 0.0590 |
| mAR@10 | 0.1275 |
| mAR@100 | 0.1322 |

Baseline показал ограниченное качество на целевом датасете: при `mAP@0.5 = 0.1363` модель частично находит транспортные объекты, но без fine-tuning плохо адаптирована к разметке и классам Udacity Self Driving Car Dataset. Это подтверждает необходимость дообучения модели на целевых данных.

Baseline-эксперимент находится в ноутбуке:

```text
notebooks/02_baseline_detection.ipynb
```

### Основные detection-модели

В основном экспериментальном ноутбуке проводились эксперименты с detection-моделями torchvision.

Использовались модели:
- `fasterrcnn_resnet50_fpn`;
- `fasterrcnn_mobilenet_v3_large_fpn`;
- `retinanet_resnet50_fpn`.

Основные эксперименты находятся в ноутбуке:

```text
notebooks/03_detection_experiments.ipynb
```

В ходе экспериментов оценивались:
- качество локализации;
- качество классификации объектов;
- `precision@0.5`;
- `recall@0.5`;
- `f1@0.5`;
- `mAP@0.5`;
- скорость и практическая применимость модели.

### Финальная модель

В качестве финальной модели выбрана:

```text
fasterrcnn_resnet50_fpn
```

Финальная модель была выбрана по результатам экспериментов, основной критерий - значение `mAP@0.5` на validation-части.

## 5. Экспериментальный протокол и результаты

### Экспериментальный протокол

Данные делились на train/validation по изображениям, а не по отдельным строкам аннотаций. Это важно для обнаружения объектов: все bounding boxes одного изображения должны попадать либо в train, либо в validation.

В экспериментах использовались:
- фиксированный seed для воспроизводимости;
- train/validation split;
- detection transforms;
- evaluation по IoU threshold `0.5`;
- выбор лучшей модели по `mAP@0.5`;
- early stopping;
- сохранение лучшего checkpoint и metadata.

### Сравнение моделей 

| Модель / конфигурация | Описание | precision@0.5 | recall@0.5 | f1@0.5 | mAP | mAP@0.5 | mAP@0.75 | Комментарий |
|---|---|---:|---:|---:|---:|---:|---:|---|
| Baseline Faster R-CNN COCO | Pretrained COCO, без fine-tuning на Udacity | 0.3562 | 0.5310 | 0.4264 | 0.0646 | 0.1363 | 0.0533 | Стартовая pretrained-модель, оценена на 300 val-изображениях |
| Faster R-CNN ResNet50 FPN | Fine-tuning на Udacity | 0.7040 | 0.8324 | 0.7628 | 0.3644 | 0.6765 | 0.3453 | Финальная модель |
| Faster R-CNN MobileNetV3 FPN | Fine-tuning на Udacity | 0.7490 | 0.7364 | 0.7427 | 0.3088 | 0.5640 | 0.2929 | Более лёгкая архитектура, выше precision, но ниже recall и mAP@0.5 |
| RetinaNet ResNet50 FPN | Fine-tuning на Udacity | 0.6843 | 0.7506 | 0.7159 | 0.2395 | 0.4535 | 0.2239 | One-stage detector, уступил Faster R-CNN по mAP@0.5 |

При интерпретации результатов важно учитывать, что baseline был рассчитан на ограниченной validation-подвыборке, а обученные модели оценивались в основном экспериментальном протоколе.

По результатам сравнения видно, что baseline-модель без fine-tuning показала существенно более низкое качество: `mAP@0.5 = 0.1363`. Это ожидаемо, так как модель была обучена на COCO и не адаптировалась к классам и распределению объектов Udacity Self Driving Car Dataset.

После fine-tuning на целевом датасете качество значительно выросло. Финальная модель `Faster R-CNN ResNet50 FPN` достигла `mAP@0.5 = 0.6765`, `recall@0.5 = 0.8324` и `f1@0.5 = 0.7628`.

Сравнение обученных моделей показывает, что `Faster R-CNN MobileNetV3 FPN` имеет немного более высокий `precision@0.5 = 0.7490`, однако уступает по `recall@0.5`, `f1@0.5` и ключевой метрике `mAP@0.5`. Это означает, что MobileNet-модель делает меньше ложных срабатываний, но хуже покрывает реальные объекты и в целом уступает по качеству detection.

`RetinaNet ResNet50 FPN` показала худшее качество среди обученных моделей по `mAP@0.5 = 0.4535`, поэтому не была выбрана финальной моделью.

Итоговый выбор сделан в пользу `Faster R-CNN ResNet50 FPN`, так как она показала лучший баланс качества локализации и полноты обнаружения объектов, а также максимальное значение основной метрики `mAP@0.5`.

### Выбор финальной модели

Финальной моделью выбрана `fasterrcnn_resnet50_fpn`.

Основная причина выбора - лучшее значение ключевой detection-метрики `mAP@0.5`:

```text
mAP@0.5 = 0.6765
```

Также модель показала высокий `recall@0.5 = 0.8324`, что важно для задачи детекции объектов: лучше найти больше реальных объектов, чем пропускать значительную часть транспорта или участников движения.

При этом `precision@0.5 = 0.7040` показывает приемлемый уровень ложных срабатываний, а `f1@0.5 = 0.7628` подтверждает хороший баланс precision и recall.

По сравнению с альтернативами:
- `fasterrcnn_mobilenet_v3_large_fpn` имела более высокий precision, но уступила по `mAP@0.5` и recall;
- `retinanet_resnet50_fpn` уступила по большинству ключевых метрик;
- baseline без fine-tuning значительно уступил всем дообученным моделям.

Trade-off финальной модели состоит в том, что `Faster R-CNN ResNet50 FPN` тяжелее некоторых альтернатив, но обеспечивает лучшее качество detection, что в рамках проекта является более важным критерием.

## 6. Архитектура решения и сервис

### Архитектура пайплайна

```text
Kaggle dataset
    ↓
download
    ↓
data/raw/
    ↓
organize
    ↓
data/organized/
    ↓
prepare
    ↓
data/processed/detection/
    ↓
EDA / baseline / experiments
    ↓
training
    ↓
artifacts/models/best_detector.pt
artifacts/metrics/best_detector_meta.json
    ↓
inference
    ↓
FastAPI service
```

Основной код проекта расположен в `src/`.

Ключевые модули:
- `src/data/` - загрузка, организация и подготовка данных;
- `src/data/datasets/` - detection dataset;
- `src/data/loaders.py` - dataloaders;
- `src/data/transforms.py` - transforms для detection;
- `src/models/detection_model.py` - построение detection-модели;
- `src/models/train_detection.py` - повторное обучение модели;
- `src/models/evaluate_detection.py` - evaluation detection-моделей;
- `src/models/inference_detection.py` - загрузка модели из artifacts;
- `src/models/predict_detection.py` - prediction utilities;
- `src/api.py` - FastAPI сервис;
- `src/logger.py` - логирование.

### API и endpoints

Реализованы endpoints:

#### `GET /health`

Проверка состояния сервиса.

Возвращает:
- статус;
- имя сервиса;
- модель;
- device;
- количество классов.

#### `GET /info`

Возвращает информацию о текущей модели:
- model name;
- task;
- dataset;
- список классов;
- пути к artifacts;
- основные метрики из metadata.

#### `POST /predict`

Основной endpoint для inference.

Принимает:
- изображение;
- `score_threshold`.

Возвращает:
- имя модели;
- размер изображения;
- количество найденных объектов;
- список detections.

Каждый detection содержит:
- `label_id`;
- `label_name`;
- `score`;
- `bbox`.

#### `POST /visualize-detections`

Endpoint для визуализации результатов.

Принимает:
- исходное изображение;
- JSON-ответ из `/predict` текстом или JSON-файлом.

Возвращает изображение с нарисованными bounding boxes.

### CLI-интерфейс

Помимо REST API, в проекте реализован CLI-интерфейс на базе Typer.

Основные команды:

```bash
uv run python -m src.cli paths
uv run python -m src.cli download-weights
uv run python -m src.cli check-artifacts
uv run python -m src.cli run-api
uv run python -m src.cli predict-image --image path/to/image.jpg
```

Также реализована безопасная команда повторного обучения модели:

```bash
uv run python -m src.cli train-detector \
  --confirm-retrain \
  --confirm-long-run
```

Команда обучения требует явных подтверждений, так как процесс может занимать несколько часов и потенциально может привести к замене текущей лучшей модели. Для замены `best_detector.pt` требуется дополнительный флаг `--confirm-overwrite-best`.

## 8. Ограничения и дальнейшая работа

### Ограничения текущей версии

- inference выполняется только для изображений;
- отсутствует batch inference;
- отсутствует video inference;
- модель работает только с классами, представленными в обучающем датасете;
- inference-сервис использует одну финальную модель;
- повторное обучение реализовано отдельным модулем, но не запускается автоматически из API;
- полноценный production-мониторинг не реализован;
- Docker deployment пока не добавлен.

### Возможные направления развития

В дальнейшем проект можно расширить:
- добавить batch inference;
- добавить video inference;
- добавить Dockerfile и docker-compose;
- расширить логирование до production-мониторинга;
